# Spec: Per-daemon keystore unlock keys

This document is the confirmed design. All implementation must follow it.

## Problem today

- The "unlock key" for a daemon's credential keystore is secretly the *client's own*
  X25519 keypair (`~/.config/choreographr/identity.pk` / `public.pk`, generated by
  `choreo_keystore::ensure_keypair`). Credential blobs in the daemon DB are encrypted
  with `choreo_keystore::crypto::encrypt_with_public_key(&client_public_key, ...)`,
  and the daemon decrypts them with the private key a client sends via
  `ClientMessage::Unlock { private_key }`. `AddCredential` carries an *optional*
  `unlock_key` (the raw client private key) so the daemon can decrypt immediately.
- `identity.pk`/`public.pk` serve NO other purpose (not transport, not ACL).

## Target design (confirmed with the user)

1. **Each daemon's keystore is governed by ONE keypair belonging to that daemon.**
   The daemon stores only a *binding*: the 32-byte X25519 public key derived from
   the keystore private key. The private key ("unlock key") is held client-side,
   one per daemon.
2. **Binding is established by first insertion** (TOFU):
   - First valid `Unlock { private_key }` or `AddCredential { ..., unlock_key }`
     against an *unbound* keystore ADOPTS the presented key: the daemon derives the
     public key, persists the binding, and logs loudly (`info!`) that binding occurred.
   - Every later `Unlock`/`AddCredential` must present a key whose derived public
     key equals the binding; mismatches are rejected (`LockedError` for Unlock,
     an error reply for AddCredential).
3. **`AddCredential.unlock_key` becomes REQUIRED** (`Vec<u8>`, not `Option`) — the
   credential must be usable immediately. Daemon-side flow on receipt:
   a. derive pubkey from `unlock_key`; adopt or verify against binding (as above);
   b. **test-decrypt** the incoming blob with the key
      (`choreo_keystore::crypto::decrypt_with_private_key`); a blob that does not
      decrypt is REJECTED and never persisted (this enforces "same encryption key
      as the rest of the keystore");
   c. persist the blob (`db::set_credential_blob`);
   d. **implicit unlock**: decrypt ALL stored credential blobs with the key into
      `state.credentials`, load accounts, resolve providers (same tail as
      `handle_unlock_inner`). A valid `AddCredential` to a locked daemon unlocks it.
4. **Client stores one unlock key per daemon**, paired with the daemon's entry in
   `known_servers.toml` (`KnownServerEntry` gains an optional `unlock_key` field,
   base64, same encoding conventions as `pubkey`).
   - Lookup/record keyed by the connection's addr string. TCP connections use the
     existing `host:port` addr; Unix-socket connections use the socket path as the
     addr key (see "Unix socket" note below).
   - Key resolution order for any Unlock/AddCredential to daemon at `addr`:
     1. stored `unlock_key` from known_servers entry for that addr;
     2. LEGACY fallback: raw `identity.pk`, or `identity.pk.enc` decrypted with
        `CHOREOGRAPHR_KEYSTORE_PASSPHRASE` (migration for existing local setups —
        the daemon adopts it on first unlock, all existing blobs keep decrypting);
     3. (AddCredential only) generate a FRESH random 32-byte key.
   - **Recording**: normally the client persists the key ONLY after the daemon
     CONFIRMS success (`Unlocked` / `CredentialAdded` reply) — replacing any
     legacy value and, when it came from the legacy fallback, deleting
     `identity.pk` / `identity.pk.enc`. The one exception is a FRESH key minted at
     step 3: it is OPTIMISTICALLY recorded immediately, because a fresh key is
     adopted TOFU by an unbound daemon and a LOST confirmation would otherwise
     strand the client with no way to recover the binding. That optimistic record
     is PROVISIONAL but PERMANENT-until-replaced: a daemon rejection
     (`LockedError` / `CredentialAddFailed`) does NOT delete it. There is NO
     programmatic revert, deliberately:
     (a) the keystore binding is TOFU-once and never rotates, so a CONFIRMED
     record can never be wrong later;
     (b) the daemon surfaces EVERY unlock-path error (including transient
     failures like a database read error) as the same rejection, so a rejection
     is not proof the key is bad — deleting could erase a good confirmed key
     with no legacy fallback left;
     (c) for the one genuinely-wrong case (a fresh key rejected by an
     already-bound daemon) deletion recovers nothing — the next attempt mints
     yet another fresh key that is also rejected. The wrong key simply sits in
     `known_servers.toml` replaying its rejection until the operator replaces
     it: manual re-pair via `KnownServers::remove(addr)` (or editing the file)
     is the one recovery path. Clients drop the in-flight pending key on a
     rejection (zeroized) so a later confirmation cannot mis-attribute it.
     (Similarly, `known_servers.pin` preserves any
     stored unlock key on a re-pin — the two fields are independent.)
   - Blob encryption: client derives the public key from the unlock key locally
     (`x25519_dalek::PublicKey::from(&StaticSecret::from(key))`) and encrypts the
     serialized credential with `encrypt_with_public_key(&derived_pub, &plaintext)`.
     The crypto layer is unchanged; only which pubkey is fed in changes.
5. **Locked behavior is unchanged (soft)**: clients can connect to locked daemons;
   session ops work; inference fails until unlocked. No hard exit.
6. **Removal**: `identity.pk`/`public.pk` are removed from the codebase:
   - delete `choreo_keystore::ensure_keypair`, `paths::public_key_path`,
     `client_core::read_public_key_bytes`;
   - KEEP `paths::private_key_path` and `paths::private_key_enc_path` (legacy
     fallback read only);
   - remove the TUI's `ensure_keypair()` startup call.
7. **Terminology**: the daemon's transport public key is "pinned to the daemon's
   address" in known_servers.toml. Do NOT use the word "fingerprint" in new
   docs/comments (the `choreo_transport::key::fingerprint` helper still exists in
   code; leave it alone).
8. **Out of scope**: `choreo-content` (do not touch), client-side at-rest encryption
   of stored unlock keys (later).

## Unix socket note

Unix-socket connections have no pinned transport key. Their known_servers entry
(addr = socket path, e.g. from `choreo_proto::socket_path()`) may have
`pubkey = None` (see below) — the entry exists purely to carry the unlock key.
The IK/pin lookup path (`KnownServers::lookup`) is only called for TCP; make
`pubkey` an `Option<String>` so unix entries are representable:
- `KnownServerEntry { addr, pubkey: Option<String>, unlock_key: Option<String> }`
- `parse_store`: entries with a `pubkey` that fails to decode to 32 bytes are
  still dropped; entries with NO pubkey are kept (unix-socket unlock-key carriers).
- `lookup(addr)`: entry with `Some(valid pk)` decodes as today; `None` pubkey
  yields `Ok(None)` (first-contact semantics — TCP callers treat that as unpinned,
  unchanged).
- New methods: `unlock_key(addr) -> Result<Option<[u8; 32]>>`,
  `set_unlock_key(addr, &[u8; 32]) -> Result<()>` (persist under the same advisory
  lock; update the module doc: this store now also carries per-daemon unlock keys).

## Client-core API changes (`choreo-client-core/src/credentials.rs`)

- `try_auto_unlock_key(addr: &str) -> Option<Vec<u8>>` — stored unlock_key, else
  legacy raw/enc fallback (current logic becomes the legacy half).
- `resolve_private_key(method: &UnlockMethod, addr: &str) -> Result<Vec<u8>>` —
  `UnlockMethod::Passphrase(p)` decrypts legacy `identity.pk.enc` with `p`
  (unchanged semantics); `UnlockMethod::Raw` = stored unlock_key else legacy raw
  `identity.pk`. (shell.rs `/unlock` keeps its shape.)
- `build_add_credential_message(addr: &str, service, credential_type, fields)
  -> Result<(ClientMessage, Vec<u8>)>` — returns the message AND the unlock key
  used (resolution order above; generates fresh when nothing else available).
  The `unlock: bool` parameter is REMOVED — unlock_key is always sent.
- `record_unlock_key(addr: &str, key: &[u8]) -> Result<()>` — known_servers
  `set_unlock_key`; if the key came from the legacy fallback (callers know), also
  delete the legacy key files. Exported so UIs can call it on confirmed success.

## UI call-site updates

- TUI (`choreo-tui`): remove `ensure_keypair()` call in `connection/mod.rs`;
  thread the connection's addr string (derive from `ConnectionMode` — TCP addr,
  pinned addr, or `socket_path()` for unix) into App so auto-unlock, `/unlock`
  (chat.rs), the API-key credential modal and the Substrate credential import
  (`ai_providers.rs`) resolve/record keys per-addr; track the pending unlock key
  and call `record_unlock_key` when `DaemonMessage::Unlocked` or
  `DaemonMessage::CredentialAdded` arrives.
- GUI (`choreo-gui/src/client.rs`) and IM bridge (`choreo-im`, telegram.rs):
  update to the new signatures (addr = `socket_path()`); GUI records the unlock
  key on success like the TUI; IM bridge only resolves (its `/unlock` and
  `AddCredential` paths).
- `ShellCommand::AddCredential` loses the `unlock: bool` field; `/add-key` and
  `/add-x` usage strings drop the trailing `[unlock]` argument; update echo text.

## Daemon changes

- `choreo-daemon/src/db/mod.rs`: new table `KEYSTORE: TableDefinition<&str, &[u8]>`
  ("keystore"), key `"binding"` → 32-byte pubkey. Additive — NO schema bump.
  Functions: `get_keystore_binding`, `set_keystore_binding` (+ tests).
- `handle_unlock_inner`: read binding; None → adopt (derive + persist + loud log);
  Some → derive from presented key and compare; mismatch → Err (surfaces as
  `LockedError`).
- `handle_save_credential`: signature `unlock_key: Vec<u8>` (DaemonCommand too);
  flow per Target-design 3a–3d (adopt-or-verify, test-decrypt, persist, then the
  same bulk-decrypt + provider-resolve tail as unlock). Reply `CredentialAdded`
  and broadcast the `Unlocked` status the same way a successful Unlock does.
- `server/connection.rs`: `AddCredential` arm passes the (now required) key through.
- Existing daemon tests + integration tests that send `Unlock`/`AddCredential`
  must be updated (AddCredential now requires unlock_key; also update tests that
  relied on the optional-key path).

## Wire/proto changes

- `ClientMessage::AddCredential { service, encrypted_payload, unlock_key }` —
  `unlock_key: Vec<u8>` (required). Update round-trip tests and any size limits
  in `choreo-proto/src/size.rs` if they mention the field. `Unlock` unchanged.

## Follow-up: keystore-lock awareness (persistent client banner)

Confirmed design addition (implemented): clients must know whether the daemon's
keystore is locked. The daemon tracks an authoritative `DaemonState.locked: bool`
(starts `true`; `false` after a successful Unlock or AddCredential implicit
unlock — cleared once, in the shared `unlock_tail`; `true` again on `/lock`,
which clears in-memory credentials/providers), broadcasts the current state to
ALL activity subscribers on every real transition (`DaemonMessage::Unlocked` /
`DaemonMessage::Locked` — the existing flat variants, no proto schema/profile
churn — via `handle_broadcast_activity`), and pushes the CURRENT state to each
freshly-connecting activity subscriber at subscribe time (alongside the existing
send-on-subscribe `CatalogUpdated`), so a client that connects to an
already-locked daemon learns so without waiting for a transition. The acting
client keeps its existing `send_to_writer` per-action reply; receiving the
broadcast too is idempotent.

Client-side (`choreo-tui`): `App::keystore_locked` latches `false` on
`Unlocked`, `true` on `Locked`/`LockedError` (in `handle_daemon_message`),
defaults to `true` (assume locked until told otherwise), and is NOT cleared by
the per-keypress transient status/error clear — so it drives a PERSISTENT
status-bar banner (`🔒 keystore locked`) until the daemon reports unlocked.
Startup sets a "daemon is locked — use /unlock …" status when no unlock key
resolves; submitting a `RunInput` to a locked daemon is rejected client-side
with a clear "daemon is locked — unlock it first" status instead of sending a
message that would silently fail (`/lock` re-latches the banner via the
`Locked` broadcast). While locked the status-bar context readout is suppressed,
dropping the misleading `X / ?` (the context window isn't loaded into memory).
