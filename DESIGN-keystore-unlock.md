# Spec: Per-daemon keystore unlock keys

This document is the confirmed design. All implementation must follow it.
(This spec was rewritten after implementation to match the SHIPPED model —
bind happens via a dedicated `ClientMessage::BindKeystore` wire path that is
triggered only by client AUTO-BIND; Unlock and AddCredential are strictly
verify-only.)

## Problem today (pre-design)

- The "unlock key" for a daemon's credential keystore was secretly the *client's
  own* X25519 keypair (`~/.config/choreographr/identity.pk` / `public.pk`,
  generated by `choreo_keystore::ensure_keypair`). Credential blobs in the daemon
  DB were encrypted with `choreo_keystore::crypto::encrypt_with_public_key(&client_public_key, ...)`,
  and the daemon decrypted them with the private key a client sent via
  `ClientMessage::Unlock { private_key }`.
- `identity.pk`/`public.pk` served NO other purpose (not transport, not ACL).

## Target design (confirmed with the user)

1. **Each daemon's keystore is governed by ONE keypair belonging to that daemon.**
   The daemon stores only a *binding*: the 32-byte X25519 public key derived from
   the keystore private key. The private key ("unlock key") is held client-side,
   one per daemon.
2. **Binding is created by exactly ONE wire path: `ClientMessage::BindKeystore { key }`**
   (TOFU):
   - On an *unbound* keystore, `BindKeystore` ADOPTS the presented key: the daemon
     derives the public key, persists the binding, logs loudly (`KEYSTORE BOUND`,
     `info!`), runs the shared unlock tail, and replies the targeted
     `DaemonMessage::Bound`. Bind implies unlock.
   - On an *already-bound* keystore, `BindKeystore` VERIFIES the presented key
     against the binding: a match succeeds like an unlock (`Bound` reply), a
     mismatch is rejected with the ordinary wrong-key semantics (`LockedError`) —
     never an overwrite.
   - **No other message can create a binding.** `Unlock` and `AddCredential` are
     strictly VERIFY-ONLY: against an unbound keystore they reply the targeted
     `DaemonMessage::KeystoreUnbound` (deliberately distinct from `LockedError`,
     which now means "bound but wrong key") and never adopt anything.
   - `BindKeystore` is triggered ONLY by client AUTO-BIND at connect time, when
     the daemon reports an unbound keystore (via the subscribe-time lock-state
     push or a `KeystoreUnbound` reply to an auto-unlock attempt). There is NO
     `/bind-key` user command — binding was deliberately not surfaced as a shell
     command.
3. **`AddCredential.unlock_key` is REQUIRED** (`Vec<u8>`, not `Option`) — the
   credential must be usable immediately. Daemon-side flow on receipt:
   a. verify the key against the keystore binding (an unbound keystore is
      rejected with `KeystoreUnbound` — binding happens exclusively via
      `BindKeystore`);
   b. **test-decrypt** the incoming blob with the key
      (`choreo_keystore::crypto::decrypt_with_private_key`); a blob that does not
      decrypt is REJECTED and never persisted (this enforces "same encryption key
      as the rest of the keystore");
   c. persist the blob (`db::set_credential_blob`);
   d. **implicit unlock**: decrypt ALL stored credential blobs with the key into
      `state.credentials`, load accounts, resolve providers (same tail as the
      unlock path — the shared `unlock_tail`). A valid `AddCredential` to a
      locked daemon unlocks it. `unlock_key` exists so the credential is
      available in RAM immediately.
4. **Client stores one unlock key per daemon**, paired with the daemon's entry in
   `known_servers.toml` (`KnownServerEntry` has an optional `unlock_key` field,
   base64, same encoding conventions as `pubkey`).
   - Lookup/record keyed by the connection's addr string. TCP connections use the
     existing `host:port` addr; Unix-socket connections use the socket path as the
     addr key (see "Unix socket" note below).
   - **Binding keys are ALWAYS freshly generated** by the client's CSPRNG at bind
     time (`bind_fresh_daemon` mints a 32-byte key with `rand::random`). Pre-held
     keys — the stored known_servers `unlock_key` or the legacy raw `identity.pk`
     file — are unlock-VERIFICATION keys only: they verify existing bindings,
     they NEVER create new ones. The legacy `identity.pk` is unlock-only per
     decision and is never deleted.
   - Key resolution order for any Unlock/AddCredential to daemon at `addr`
     (VERIFY-ONLY — no fresh-key minting anywhere in this chain):
     1. stored `unlock_key` from known_servers entry for that addr;
     2. LEGACY fallback: the raw `identity.pk` file — whose key is COPIED
        into the known_servers entry on first use (the store becomes the
        single source of truth; the legacy file is NEVER deleted).
        (`identity.pk.enc` + `CHOREOGRAPHR_KEYSTORE_PASSPHRASE` decryption
        has been REMOVED entirely.)
     When neither source has a key the resolution errors with
     `ClientError::NoUnlockKey` and the frontend surfaces it. The daemon is
     either unbound (the client auto-binds first, see below) or bound to a key
     this client does not hold.
   - **Recording rules** (client-side discipline, shared by TUI/GUI/IM via the
     pending-key flow):
     - A BIND key (freshly minted by `bind_fresh_daemon`) is recorded into
       known_servers PRE-SEND — this is MANDATORY and the bind is REFUSED if the
       store write fails (sending an unrecorded bind key risks an unrecoverable
       orphaned binding). Pre-send is CORRECT for bind and only for bind: an
       unbound daemon adopts whatever key arrives first, so even a LOST
       confirmation leaves the recorded key matching the binding — there is
       nothing to overwrite and nothing to lose.
     - Unlock and AddCredential keys are recorded ONLY on the daemon's targeted
       confirmation (`Unlocked` / `Bound` / `CredentialAdded`), via the
       `PendingUnlock`-style pending key held in the frontend and passed to
       `record_unlock_key`. Nothing is written to known_servers on send, so a
       key the daemon rejects never pollutes the store. (`UnlockMethod::Key`
       from `/unlock <key>` is likewise write-free — supplied keys never bind
       and never record until confirmed.)
     - NOTHING is ever auto-deleted. A rejection (`LockedError` /
       `CredentialAddFailed`) drops the in-flight pending key (zeroized) so a
       later confirmation cannot mis-attribute it, but leaves any stored record
       untouched. PROVISIONAL (never-confirmed) records persist and are benign:
       the store semantics are "`unlock_key` = the key the client intends to use,
       provisionally until the daemon confirms it". Because the binding is
       TOFU-once and never rotates, a CONFIRMED record can never become wrong
       later; and the daemon surfaces every unlock-path error (including
       transient failures like a database read error) as the same rejection, so
       a rejection is not proof the key is bad — deleting could erase a good
       confirmed key with no legacy fallback left. Manual re-pair via
       `KnownServers::remove(addr)` (or editing the file) is the one removal
       path — pin and unlock key go together.
       (Similarly, `known_servers.pin` preserves any stored unlock key on a
       re-pin — the two fields are independent.)
   - Blob encryption: client derives the public key from the unlock key locally
     (`x25519_dalek::PublicKey::from(&StaticSecret::from(key))`) and encrypts the
     serialized credential with `encrypt_with_public_key(&derived_pub, &plaintext)`.
     The crypto layer is unchanged; only which pubkey is fed in changes.
5. **ORDERING INVARIANT (wire-level contract).** The targeted reply to
   `Unlock` / `BindKeystore` / `AddCredential` is enqueued by the daemon command
   loop into the acting client's writer sink BEFORE any lock-state transition
   broadcast — both travel the same per-client FIFO writer queue, so the
   broadcast can never overtake the reply. Client key-recording correctness keys
   on this: the client records its pending key when the targeted
   `Unlocked`/`Bound`/`CredentialAdded` arrives, and the idempotent
   `Unlocked` broadcast copy must not arrive (on the acting client) before the
   targeted reply. Implemented via `DaemonCommand` carrying the acting client's
   `SubscriberSink` (the `send_targeted` helper on `DaemonState`); documented at
   each send site in `choreo-daemon/src/daemon.rs` and pinned by the integration
   test `unix_targeted_reply_precedes_lock_state_broadcast`
   (`choreo-daemon/tests/daemon_client_unix.rs`).
6. **Locked behavior is unchanged (soft)**: clients can connect to locked daemons;
   session ops work; inference fails until unlocked. No hard exit.
7. **Removal**: `identity.pk`/`public.pk` generation is removed from the codebase:
   - `choreo_keystore::ensure_keypair`, `paths::public_key_path`, and
     `client_core::read_public_key_bytes` are deleted;
   - `paths::private_key_path` (the legacy raw file) is KEPT as an
     unlock-VERIFICATION fallback only — it is never deleted, never binds;
   - the TUI's `ensure_keypair()` startup call is removed;
   - encrypted-key resolution (`identity.pk.enc` +
     `CHOREOGRAPHR_KEYSTORE_PASSPHRASE`) was removed entirely.
8. **Auto-bind is once per connection per frontend**: a `keystore_bind_attempted`
   latch (TUI `App` field, GUI state) guarantees a repeat `KeystoreUnbound`
   after the bind attempt is surfaced as an error ("keystore still unbound after
   bind attempt — reconnect to retry"), never a re-bind loop.
9. **Terminology**: the daemon's transport public key is "pinned to the daemon's
   address" in known_servers.toml. Do NOT use the word "fingerprint" in new
   docs/comments (the `choreo_transport::key::fingerprint` helper still exists in
   code; leave it alone).
10. **Out of scope**: `choreo-content` (do not touch), client-side at-rest
    encryption of stored unlock keys (later), and **key rotation** — the binding
    is TOFU-once and NOT implemented as rotatable. A future
    `RotateUnlockKey` follow-up is made cleaner by binding being confined to one
    wire path.

## Multi-client provisioning & lifecycle

- **First client wins**: the first client to connect to a fresh (unbound) daemon
  auto-binds it with a minted key. Other clients that connect afterwards get
  `LockedError` (bound but wrong key) until the key is shared out-of-band — add
  the first client's base64 `unlock_key` to their `known_servers.toml` entry, or
  use `/unlock <base64-key>` on each.
- **Daemon DB reset**: invalidates the binding (it lived in the DB). The next
  connect reports `KeystoreUnbound` and auto-binds a fresh key; the stale stored
  key is dead weight, replaced in-place by the new bind's pre-send record.
- **Provisional records**: a known_servers `unlock_key` that was never confirmed
  (e.g. recorded pre-send for a bind whose confirmation was lost, or a key the
  daemon rejected) persists harmlessly — on a still-unbound daemon the bind
  simply adopts it; on a bound daemon it replays its rejection until the
  operator re-pairs.

## Unix socket note

Unix-socket connections have no pinned transport key. Their known_servers entry
(addr = socket path, e.g. from `choreo_proto::socket_path()`) may have
`pubkey = None` (see below) — the entry exists purely to carry the unlock key.
The IK/pin lookup path (`KnownServers::lookup`) is only called for TCP; make
`pubkey` an `Option<String>` so unix entries are representable:
- `KnownServerEntry { addr, pubkey: Option<String>, unlock_key: Option<String> }`
- `parse_store`: entries with a `pubkey` that fails to decode to 32 bytes are
  still dropped; entries with NO pubkey are kept (unix-socket unlock-key carriers).
- `lookup(addr)`: entry with `Some(valid pk)` decodes as today; `None` pubkey
  yields `Ok(None)` (first-contact semantics — TCP callers treat that as unpinned,
  unchanged).
- New methods: `unlock_key(addr) -> Result<Option<[u8; 32]>>`,
  `set_unlock_key(addr, &[u8; 32]) -> Result<()>` (persist under the same advisory
  lock; update the module doc: this store now also carries per-daemon unlock keys).

## Client-core API (`choreo-client-core/src/credentials.rs`)

- `try_auto_unlock_key(addr: &str) -> Option<Vec<u8>>` — stored unlock_key, else
  the legacy raw `identity.pk` fallback (COPIED into the store on first use).
  VERIFY-ONLY sources; `None` means the daemon starts locked, which is fine.
- `bind_fresh_daemon(addr: &str) -> Result<([u8; 32], ClientMessage)>` — the
  AUTO-BIND entry point: mints a fresh CSPRNG 32-byte key, records it into
  known_servers for `addr` PRE-SEND (mandatory — a failed store write refuses
  the bind), and returns the key plus the `ClientMessage::BindKeystore` to send.
  Callers hold the key pending and confirm via `record_unlock_key` on the
  targeted `DaemonMessage::Bound` reply (a no-op-safe re-record of the
  already-persisted key, keeping the pending-flow contract uniform).
- `resolve_private_key(method: &UnlockMethod, addr: &str) -> Result<Vec<u8>>` —
  `UnlockMethod::Raw` = stored unlock_key else legacy raw `identity.pk`
  (adopted into the store), erroring with `NoUnlockKey` when neither exists;
  `UnlockMethod::Key(b64)` = the caller-supplied base64 32-byte unlock key,
  decoded and validated WRITE-FREE — recording happens only on the daemon's
  confirmed `Unlocked` reply, and a supplied key can never create a binding.
  (`UnlockMethod::Passphrase` — identity.pk.enc decryption — was removed.)
- `build_add_credential_message(addr: &str, service, credential_type, fields)
  -> Result<(ClientMessage, Vec<u8>)>` — returns the message AND the unlock key
  used (VERIFY-ONLY resolution order above; `NoUnlockKey` when nothing
  resolves — there is NO fresh-mint fallback; fresh keys are minted exclusively
  by `bind_fresh_daemon`). The `unlock: bool` parameter is REMOVED —
  unlock_key is always sent.
- `record_unlock_key(addr: &str, key: &[u8]) -> Result<()>` — known_servers
  `set_unlock_key`. Callers MUST only invoke this after the daemon CONFIRMED
  the key (`Unlocked` / `Bound` / `CredentialAdded`) — never on send. Legacy
  files are NEVER touched: no comparison, no deletion — the store supersedes
  them once it holds the key.

## UI call-site updates

- TUI (`choreo-tui/src/connection/daemon.rs`): `handle_daemon_message` holds the
  pending unlock key (`app.pending_unlock_key`) set by auto-unlock, the
  chat/credential handlers, and the auto-bind arm; `Unlocked`/`Bound`/
  `CredentialAdded` record it via `record_unlock_key`, `KeystoreUnbound` drops
  it and triggers the once-per-connection auto-bind, `LockedError`/
  `CredentialAddFailed` drop it without touching the store. The TUI `/unlock`
  command has NO `[bind]` variant and there is no `/bind-key`.
- GUI (`choreo-gui/src/client.rs`): same pending-key flow on
  `Unlocked`/`Bound`/`CredentialAdded` confirmations, same
  `keystore_bind_attempted` bind-loop guard on `KeystoreUnbound`.
- IM bridge (`choreo-im`): resolves the stored/legacy key for unlock and
  `AddCredential`; on `KeystoreUnbound` — or with NO key available at all — it
  PROBES with a fresh bind (`bind_fresh_daemon`), which is safe because
  `BindKeystore` against a bound keystore is rejected without overwrite (it can
  only ever create a binding that did not exist, and pre-send recording means
  the minted key is never lost).
- `ShellCommand::AddCredential` has no `unlock: bool` field; `/add-key` and
  `/add-x` usage strings have no trailing `[unlock]` argument.

## Daemon changes

- `choreo-daemon/src/db/mod.rs`: table `KEYSTORE: TableDefinition<&str, &[u8]>`
  ("keystore"), key `"binding"` → 32-byte pubkey. Additive — NO schema bump.
  Functions: `get_keystore_binding`, `set_keystore_binding` (+ tests).
- `handle_unlock_inner`: read binding; `None` → `Err(KeystoreOpError::Unbound)`
  (surfaces as the targeted `KeystoreUnbound`); `Some` → derive from the
  presented key and compare; mismatch → `Err` (surfaces as `LockedError`); match
  → the shared `unlock_tail`.
- `handle_bind_keystore_inner` (the only adoption path, used ONLY by
  `BindKeystore`): unbound → TOFU-adopt (derive + persist + loud
  `KEYSTORE BOUND` log); bound → verify, mismatch rejected; match → the shared
  `unlock_tail` (bind implies unlock). Replies the targeted `DaemonMessage::Bound`.
- `handle_save_credential`: signature `unlock_key: Vec<u8>` (DaemonCommand too);
  flow per Target-design 3a–3d (verify-only, test-decrypt, persist, then the
  same bulk-decrypt + provider-resolve `unlock_tail` as unlock). Reply
  `CredentialAdded` and broadcast the `Unlocked` status the same way a
  successful Unlock does.
- **Ordering**: `Unlock`, `BindKeystore`, and `AddCredential` `DaemonCommand`s
  carry the acting client's `Option<SubscriberSink>`; the daemon command loop
  enqueues the targeted reply into it BEFORE the lock-state transition
  broadcast (see the ORDERING INVARIANT above).
- `server/connection.rs`: the `AddCredential` arm passes the (required) key and
  the client writer through; `BindKeystore` likewise.
- Keystore error taxonomy: `KeystoreOpError::Unbound` → `KeystoreUnbound`;
  everything else → `LockedError` ("bound but wrong key" or a transient
  failure rendered through the same variant).

## Wire/proto changes

- `ClientMessage::BindKeystore { key }` — NEW; the only binding path.
- `ClientMessage::AddCredential { service, encrypted_payload, unlock_key }` —
  `unlock_key: Vec<u8>` (required).
- `DaemonMessage::Bound` — NEW targeted confirmation that an unbound keystore
  adopted a `BindKeystore` key and the implicit unlock succeeded (distinct from
  `Unlocked` so the client can tell "I just created this binding" from "I
  verified an existing one").
- `DaemonMessage::KeystoreUnbound { error }` — NEW targeted error for
  Unlock/AddCredential/BindKeystore against an unbound keystore (distinct from
  `LockedError`, which means "bound but wrong key").

## Follow-up: keystore-lock awareness (persistent client banner)

Confirmed design addition (implemented): clients must know whether the daemon's
keystore is locked. The daemon tracks an authoritative `DaemonState.locked: bool`
(starts `true`; `false` after a successful Unlock, BindKeystore, or AddCredential
implicit unlock — cleared once, in the shared `unlock_tail`; `true` again on
`/lock`, which clears in-memory credentials/providers), broadcasts the current
state to ALL activity subscribers on every real transition
(`DaemonMessage::Unlocked` / `DaemonMessage::Locked` — the existing flat
variants, no proto schema/profile churn — via `broadcast_lock_state`), and pushes
the CURRENT state to each freshly-connecting activity subscriber at subscribe
time (alongside the existing send-on-subscribe `CatalogUpdated`), so a client
that connects to an already-locked daemon learns so without waiting for a
transition. The acting client keeps its existing targeted reply; receiving the
broadcast too is idempotent (and, per the ORDERING INVARIANT above, always
arrives after it).

Client-side (`choreo-tui`): `App::keystore_locked` latches `false` on
`Unlocked`/`Bound`, `true` on `Locked`/`LockedError` (in `handle_daemon_message`),
defaults to `true` (assume locked until told otherwise), and is NOT cleared by
the per-keypress transient status/error clear — so it drives a PERSISTENT
status-bar banner (`🔒 keystore locked`) until the daemon reports unlocked.
Startup sets a "daemon is locked — use /unlock …" status when no unlock key
resolves; submitting a `RunInput` to a locked daemon is rejected client-side
with a clear "daemon is locked — unlock it first" status instead of sending a
message that would silently fail (`/lock` re-latches the banner via the
`Locked` broadcast). While locked the status-bar context readout is suppressed,
dropping the misleading `X / ?` (the context window isn't loaded into memory).
